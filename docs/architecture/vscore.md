# V-Score in full

> Moved verbatim out of CLAUDE.md on 2026-09-24 to keep that file under the size Claude Code loads comfortably. These are still binding project decisions; CLAUDE.md keeps a one-line summary of each and points here.

## V-Score (spec is final)

Bands: **Elite 90+ · Trusted 75–89 · Active 60–74 · Developing 40–59 · At Risk <40.** New volunteers start at 70. After each event review: new_score = 0.7×old + 0.3×event_outcome, where event_outcome is derived from attendance + reliability_score + clinical_score. Penalties: late cancellation −8, on-time cancellation −2. Recomputed only by the serverless `/api/vscore` endpoint — never on the client.

**THE "no-show −15" THAT USED TO BE IN THAT LIST WAS NEVER APPLIED, and the line is corrected here (2026-09-23) rather than deleted, because the contradiction it caused is worth remembering.** This section said "no-show −15" while the `score_events` section two screens down said `no_show` "IS NOT A KIND, and never becomes one" — both written truthfully at different times, neither updated when the other changed, exactly the failure the multi-day section warns about. The code implements the second: an absence is expressed by a review filed with `attended: false`, which floors that event's outcome to 0, and the blend then makes the new score `0.7 × old`. So the real cost is a PROPORTION, not a fixed subtraction, and it is BIGGER than 15 points for anyone above 50 (70 becomes 49; 90 becomes 63). `V_SCORE_PENALTIES.no_show` still exists in `lib/vscore.ts` and has no production caller. **The volunteer Info Hub was printing that −15 to volunteers as the cost of a no-show**, which understated the worst penalty in the app to precisely the people it exists to deter; it now describes the mechanism instead.

### The score is DERIVED, not a running total (owner-approved 2026-08-26)

**`volunteer_profiles.v_score` is a CACHE. The truth is `event_reviews` plus any upheld `disputes`.** The formula above is unchanged; what changed is that it is applied to the volunteer's WHOLE history from 70 on every write, instead of being blended once into whatever number was already stored. `replayVScore` in `lib/vscore.ts` is the pure rule; `api/src/server/vscoreReplay.ts` is the only thing that reads history and writes the cache; `supabase/migrations/20260903a` (dry run) and `20260903b` (the write) rebuilt every existing score.

- **Why, beyond disputes.** A running total has no way back — one wrong review was permanent. It was also **already subtly wrong**: `event_reviews` is upserted on `(outreach_id, volunteer_id)`, so an organisation EDITING a review it had already filed blended a second time into a score the first version had already moved, and incremented `events_attended` again. Replaying fixes that without anyone having had to notice it.
- **The order is FILING order** — `event_reviews.created_at`, tie-broken by `id` — **never the outreach's date.** The blend is order-dependent, so replaying by event date would re-insert a January event reviewed in June ahead of events already counted, moving a score for a reason unconnected to any error. Filing order also means the replay must reproduce the stored score EXACTLY for anyone with no upheld dispute, which is what made the migration's dry run self-checking.
- **An upheld dispute VOIDS that event** rather than replacing its ratings with better ones. An upheld attendance dispute additionally counts it as attended.
- **`events_attended` is derived too**, for the same reason: it was incremented per review, so an edited review counted twice.
- **`v_score_recomputed_at` records when the cache was last rebuilt.** Server-only, in no grant list. A derived value nothing records the age of is indistinguishable from a stale one.
- **THE REPLAY IS THE ONLY WRITER.** Nothing anywhere does arithmetic on the stored score. Every write — a review, a penalty, an upheld dispute — records the FACT and then replays.
- **`score_events` is where the flat penalties live** (owner-approved 2026-08-27, `supabase/migrations/20260904_score_events.sql`). They produce no `event_reviews` row, so before it existed a deduction was written onto the stored number and the next replay erased it silently. `/api/vscore`'s `penalty` and `late_release` actions write a row there, then replay. See the section below.

### The outcome is scaled by the days actually attended (owner-approved 2026-08-30)

**`event_outcome` is computed ONCE per event, then multiplied by `days_attended / days_committed`.** Before this, the whole multi-day subsystem recorded which days a volunteer promised and which they turned up for, and the scorer discarded all of it: 1 day of 4 scored identically to 4 of 4. `dayCommitmentRatio` in `lib/vscore.ts` is the rule; `computeEventOutcome` applies it; `vscore_day_ratio()` mirrors it in SQL (`supabase/migrations/20260906a`, dry run, and `20260906b`, the write).

- **Once per event, never once per day.** `event_reviews` is unique on `(outreach_id, volunteer_id)`, so there is one outcome per event structurally. Scoring per day would let a month-long campaign move a score twenty times harder than a one-day clinic — a statement about the event's length, not about the volunteer.
- **The denominator EXCLUDES released days.** A day dropped in advance *departs* the commitment; it is not a failure and not an absence. Leaving it in the denominator would turn every honest early release into a silent penalty — the exact trap per-day release was built to remove.
- **An UNRESOLVED day counts as ATTENDED.** `isPresent` (and its SQL mirror `attendance_is_present`) default present, so a missing attendance row, or one the organiser never gave a verdict on, costs the volunteer nothing. The ratio falls only where a human actually marked somebody absent. An organiser who never opens the attendance screen cannot damage anybody's score by inaction, and a flat phone is not an absence.
- **Only ZERO attended days is a no-show**, and it gets there by arithmetic rather than by a second rule: a ratio of 0 multiplies the outcome to exactly the 0 that `attended = false` already takes. Anything above zero is a **partial attender**, scored on the share delivered.
- **Omitting the day figures means DO NOT SCALE, never "attended nothing".** `daysAttended` / `daysCommitted` are optional on `EventOutcomeInput`, and `dayCommitmentRatio` returns `null` rather than `0` when either is absent. Reading a missing number as a bad one is the mistake `DEFAULT_MISSING_SUBSCORE` made.
- **The ratio is DERIVED at replay time, never stored on the review.** The days promised and the days attended are evidence living in `application_days` and `attendance`, and they keep changing after a review is filed — an organiser resolving day 3 a week later must move the score, and it does, on the next replay. (Contrast `score_events.points`, which IS stored: a penalty's number is the decision, not evidence.)

### `score_events` — the flat penalties (owner-approved 2026-08-27)

The three deductions that produce no event review: **late cancellation −8, on-time cancellation −2, and the late per-day release** (two free in a rolling 90 days, then −8 × days released ÷ days committed, floored at −2, capped at −8). They are part of the replayable history, so a recompute preserves them.

- **`no_show` IS NOT A KIND, and never becomes one.** An absence is already expressed by a review filed with `attended: false`, which floors that event's outcome to 0. A second route to the same deduction would punish one no-show twice — the rule stated below under "Absence alone moves nothing". `/api/vscore` cannot express it: `RecordPenaltyInput.kind` is typed to the legal kinds and the enum in `20260904_score_events.sql` excludes `no_show` (the migration ends by asserting that). The `penalty` action itself was later REMOVED from `/api/vscore` altogether, so an attempt now fails as an unrecognised action rather than as a kind-level validation error. Corrected 2026-09-23; this line described the older mechanism.
- **`points` is STORED, not recomputed at replay time** — the one real asymmetry with a review, and it is deliberate. A review stores its ratings and the outcome is derived, because the review is evidence. A penalty's number IS the decision. Recomputing would let a later change to the amounts silently re-punish cancellations settled months ago; and the late-release figure depends on the rolling 90-day count **as it stood at the moment of the release**, which cannot honestly be reconstructed once the window has moved.
- **`points < 0` is a check constraint.** A free late release writes NOTHING — the fact of it lives on `application_days.late_release`, and a zero-point row would put a penalty in the volunteer's list that deducted nothing.
- **`dedupe_key` + `unique (volunteer_id, dedupe_key)` makes every write retry-safe.** A cancellation keys on the application; a late release keys on the released day **and the moment it was released**, because a day can be taken back on and dropped late again, and that is a genuinely new act. Getting this wrong is not cosmetic — it is charging somebody twice for one act.
- **A penalty is a flat subtraction at its point in the merged stream**, and later reviews blend it away at 0.7× apiece — exactly what happened when the score was a running total. **This is not a formula change.**
- **Reviews and penalties are ONE ordered stream**, merged on `created_at` with a fixed tie-break (`source_rank`: a review sorts before a penalty, then `id`). Two passes could not express "the cancellation came before the review", and that ordering decides how much of the deduction survives. `SOURCE_RANK` in `api/src/server/vscoreReplay.ts` and `source_rank` in `vscore_replay()` must stay identical.
- **Reversal is `voided_at`, never a DELETE.** The row stays, because a penalty is the evidence behind a score. A voided row stops counting — the same treatment an upheld dispute gives a review. There is deliberately **no DELETE-refusing trigger** (unlike `admin_actions`): `volunteer_id` cascades from `profiles`, and a trigger could not tell an account deletion from a bad delete.
- **Nothing is client-writable — no INSERT, UPDATE or DELETE grant at all.** A client that could insert could penalise anybody by name; one that could update could void its own penalties. Reads are the volunteer themselves and admins, **not** the organisation: it is a person's disciplinary record, and an organisation already sees the score it produced.
- **PENALTIES ARE LIVE (owner-approved 2026-08-31).** The standing hold of 2026-08-21 is lifted. See the section below for where each one is applied and why it cannot be applied anywhere else.

### Penalties, wired (owner-approved 2026-08-31)

**A CANCELLATION IS ONLY PENALISED WHEN THE VOLUNTEER HELD AN ACCEPTED PLACE.** Withdrawing a `pending` or `waitlisted` application costs nothing — no place was held, no organiser was left short, and it is the behaviour the app wants instead of somebody going quiet.

- **That fact has a lifetime of one request**, and everything below follows from it. `applications` does not record what a cancelled row used to be, so once `status` reads `'cancelled'` nothing can tell an abandoned accepted place from a withdrawn pending one.
- **So the cancellation and its deduction are ONE server operation**, in `/api/application-status`. **`useCancelApplication` no longer writes the row itself** — it used to cancel through RLS and then call the endpoint as a best-effort nudge, which consumed the previous status before the server ever saw it. The endpoint now writes the status and the `cancellation_reason` together, and the trigger stamps `cancelled_at` / `late_cancellation` as before.
- **`/api/vscore`'s `penalty` action was REMOVED for the same reason.** An endpoint asked to apply a cancellation penalty after the fact would be guessing. Do not re-add it.
- **Only the volunteer's OWN withdrawal counts.** An organisation cancelling somebody's place is the organisation's decision; moderation withdrawals do not come through this endpoint at all.
- **The failure mode changed, for the better**: the withdrawal now either happens completely or not at all, instead of leaving a cancelled application with an un-promoted waitlist. The deduction itself is best-effort *inside* the endpoint — a withdrawal is never reported as failed because a penalty could not be written.

**A LATE PER-DAY RELEASE is charged by `/api/vscore`'s `late_release` action, and backstopped nightly.**

- **The client names WHICH DAY and nothing else.** `daysReleased` and `daysCommitted` used to be request fields — they are the numerator and denominator of the deduction, so a client that could send them could choose its own penalty. Both are now counted server-side, along with the rolling 90-day allowance.
- **`daysCommitted` is EVERY `application_days` row, released or not** — the original promise, which is the denominator the approved formula was calibrated against. **`daysReleased` is always 1**: each late release is one act charged for itself, so four single-day drops of a four-day commitment total exactly −8, the withdrawal figure the formula meets at its own edge. A unit test asserts that composition.
- **The prior-releases count is taken as of `released_at`, strictly before it** — not as of now — so the nightly sweep computes the same figure the live call would have.
- **`sweepUnchargedLateReleases` runs as the FIFTH cron pass**, because releasing a day is a client write while the deduction needs the service role: an app that never makes the follow-up call would otherwise escape entirely. Deduplicated on the released day plus the moment it was released, so it can never double-charge. **The cancellation deliberately has no equivalent sweep** — there is nothing left to detect.
- **A late release is charged ONLY on an accepted application** (owner-confirmed 2026-08-31), the same rule a cancellation follows: a pending or waitlisted volunteer dropping a day has taken no place from anybody and left no organiser short.
- **`PENALTIES_LIVE_FROM` in the sweep is a permanent floor.** Releases made before penalties went live are never charged: that would be retroactive punishment arriving as a score drop with no act attached.

**Both are told to the volunteer at the moment they happen**, with the amount and the new score named, and both appear on My feedback afterwards. Nothing about a score is said when nothing was charged — "that cost you 0 points" reads as a punishment.

### Both ends of a penalty are now visible (built 2026-08-31)

A deduction could be caused and then neither inspected nor undone — the one irreversible thing left in a score model whose whole point is that it is derived. An upheld dispute could reach back and void a REVIEW; nothing could reach a PENALTY.

- **The volunteer sees their own deductions on "My feedback"** (`app/(volunteer)/feedback.tsx`), above the reviews and outside the intro card, because reviews are what people said and a deduction is what the platform did. It renders **nothing at all** when there are none, which is almost everybody.
- **The admin sees every deduction on `app/(admin)/deductions.tsx`**, pushed from Home rather than taking a sixth tab. **A LIST, not a search — the opposite of the People screen and deliberately so.** People browses accounts, and a roll of every account invites looking through them for their own sake; this browses decisions the platform already made about somebody's number, the same kind of thing as the activity log, and an admin has to be able to find a wrong one without knowing whose it was.
- **`/api/score-event` is the only way to reverse one**, admin-only, writing `voided_at` + `voided_reason`, then replaying, then an audit row, then telling the volunteer with the amount and the new score named. **It is one-way**: re-applying a deduction would be a new decision with its own reason, not the resurrection of a reversed one.
- **A reversed deduction stays visible to both**, marked reversed. Hiding it would mean somebody told about a penalty could later find no trace of it — which reads as a lost record rather than a withdrawn penalty.
- **`score_event` is a new `admin_actions.target_type`** (`supabase/migrations/20260907`). `target_type` is a CHECK rather than an enum precisely so this is a one-paste drop-and-add; this is the first time that decision was collected on. **The migration has to land with the endpoint**, because `recordAdminAction` throws on an unrecordable decision — which is correct, and is why they ship together.

**An unrated review moves nothing** (corrected 2026-08-07, owner-approved). `computeEventOutcome` returns **null** when a review carries no scorable signal — attended is true but `reliability_score` is missing, or attendance itself is unknown — and `recomputeVScoreAfterReview` then returns the old score untouched. A missing `clinical_score` is NOT a gap: support-role volunteers are never clinically scored, so reliability alone is a complete review for them.

This replaces an earlier rule that substituted a midpoint 3/5 for a missing rating "so a data gap neither rewards nor punishes the volunteer". That was wrong in effect: 3/5 scales to 60, everyone starts at 70, so an unrated review always dragged a good volunteer down (0.7×70 + 0.3×60 = 67) and repeated ones pulled anyone toward 60. **No fixed number is neutral when the baseline is 70** — the only honest response to "no rating was given" is not to move the score. The review form now requires the ratings (both, when the outreach is clinical), so this path should be unreachable from the app; it exists so a gap arriving any other way cannot quietly cost someone reputation.

**Absence alone moves nothing either** (decided 2026-08-07). Marking a volunteer absent on the attendance screen records the fact; the −15 arrives only when the review is filed with `attended: false`. One writer owns every score change, so a single no-show cannot be punished twice, and a V-Score stays derivable from its event records. Known consequence, logged in `docs/REPORT_NOTES.md`: an organisation that never reviews leaves its no-shows unpenalised.
