# Hard rules and conventions, in full


## Hard Rules (never violate)

1. **Backend is Supabase ONLY. FCM as an Android push transport is the single approved exception.**
   - **THE FCM SERVICE-ACCOUNT KEY MUST BE *ASSIGNED*, NOT MERELY UPLOADED.** Push silently failed for weeks with a valid key sitting in the Expo account attached to nothing. `eas credentials -p android` prints `Google Service Account Key assigned to com.melissaotoo.vhub for FCM V1` when it is right. It lives on Expo's servers, not in the APK, so fixing it needs NO rebuild - and equally, no rebuild will ever fix it. `eas credentials` is interactive only; there is no list or JSON flag.
   - **The ban, which stands permanently:** no Firebase for data, auth, storage, hosting, functions, analytics, or any other backend role. No Firebase SDK, no `firebase` / `@react-native-firebase/*` packages. A Firebase migration was once discussed and was permanently cancelled. Supabase remains the only backend.
   - **The exception, approved by the owner:** Firebase Cloud Messaging is used purely as the push-notification **transport** for Android. Google permits no other transport — Expo's own push service relays through FCM — so this is a platform requirement, not an architectural choice. What this means concretely: `google-services.json` lives in the repo, and the FCM service-account credential is uploaded to Expo. That is the whole footprint.
   - **`google-services.json` in the repo is CORRECT and must not be flagged as an error.** Neither must the FCM credential in Expo. Do not "fix" either by removing them — Android push stops working.
   - **What still IS an error:** a Firebase SDK dependency, Firebase Auth, Firestore/Realtime Database, Firebase Storage, Firebase Functions, or any suggestion to move backend work to Firebase. The ban was always about Firebase-as-backend; it was never about the push pipe.
2. **TypeScript strict mode everywhere.** No `any` unless truly unavoidable and commented.
3. **Matching must never halt.** Layer 1 (pure code) always runs. Layer 2 (Gemini) only enriches the skills component and silently falls back to Layer 1 on any error or quota exhaustion.
4. **Secrets never ship in the app.** The Gemini key, the Gmail app password, and the Supabase service-role key live ONLY in the serverless API (Vercel env vars). The mobile app holds only the Supabase URL + anon key via `EXPO_PUBLIC_*` env vars.
5. **Auth tokens go in Expo SecureStore**, never AsyncStorage.
6. **All user data access is governed by Supabase Row Level Security.** Every table gets RLS policies. Never disable RLS to "make it work."
   - **`profiles` INSERT is column-listed too, and was not until 2026-08-31** (`supabase/migrations/20260909`). Supabase grants `authenticated` a TABLE-LEVEL insert on everything in `public`, and a table-level grant covers **every column, including ones added later** — so a "protected by omission from the UPDATE list" column was still freely settable in the one insert that creates the row at signup. `profiles` was the only table in the schema missing an INSERT list. **The insert list is exactly `id, role, full_name, email`, and SIGNUP DEPENDS ON IT** — the app has two insert paths (`useSignUp`, `useAuthGuard`'s bootstrap) and both write those four.
   - **RLS is only half the model.** RLS decides *which rows* a client may touch; it cannot restrict *which columns*. Server-only columns (`profiles.role`; `organisation_profiles.verified`; `volunteer_profiles.v_score`, `verification_status`, `events_attended`; `applications.match_score`, `cancelled_at`, `late_cancellation`; `outreaches.slots_filled`) are protected by column-level GRANTs at the bottom of `supabase/schema.sql`. Add a new column that clients must write? Add it to the matching INSERT **and** UPDATE grant list, or writes fail.
   - **The role lock has TWO halves, and the grant list is only one of them.** The UPDATE grant list makes
     `profiles.role` immutable after signup. But the profiles row is INSERTED by the client at signup, so the
     role in that insert was always the client's to choose — harmless while the only values were the two roles
     anyone can register as, a privilege escalation the moment `'admin'` became legal. `profiles_insert_own`'s
     with-check therefore carries `and role <> 'admin'`. Never remove it, and never "fix" an admin-creation
     problem by relaxing it: admins are made by an UPDATE run in the SQL editor, which bypasses RLS.
   - **`profiles.role` is immutable after signup**, and **`organisation_profiles.verified` is service-role-only.** Both are omitted from their UPDATE grant lists on purpose. A client that could flip its own `role` could become an organisation, then self-set `verified`, then read applicant PII and move real V-Scores — that chain is closed at the database, not in the UI. Never "fix" a write failure on either column by adding it to a grant list; the write belongs in the serverless API on the service-role key.
   - The two failure modes read differently and must not be confused: a GRANT failure is `permission denied for <table>` (SQLSTATE 42501); an RLS failure is `new row violates row-level security policy for <table>`.
   - **`organisation_profiles` is the one table whose SELECT is column-listed too** (2026-09-23). Its ROWS stay world-readable (`using (true)`) because `useOutreaches` and `useApplications` EMBED it to name the organisation on a feed card, and a row-scoped policy would return null for every outreach a volunteer does not own. But the table stopped holding only public facts when verification shipped, so `authenticated` now holds SELECT on the public columns ONLY. The evidence columns (`official_email`, `physical_address`, `contact_person`, `verification_state`, `verification_reason`, the two verification timestamps, `document_consent_at`) come back through **`organisation_private_profiles`**, a `security_invoker = false` view whose `where id = auth.uid() or is_admin()` is the whole access rule. **`verified` is public and `verification_state` is not**: the boolean is the badge volunteers are meant to see, the state is not their business. Adding a column to that embed without adding it to the SELECT grant fails the WHOLE query with 42501 rather than omitting it.
   - **A review can only be filed against an ACCEPTED application** (2026-09-23), in `event_reviews_insert_org` and again in `/api/vscore`. Owning the outreach was the only test, and `public_volunteer_profiles` hands every signed-in user every volunteer's id, so an organisation could file `attended: false` against a stranger and the replay would count it: 70 to 49, once per outreach, on as many outreaches as it liked.
   - **`.upsert()` needs UPDATE on the conflict column.** PostgREST compiles `.upsert(payload, { onConflict: 'id' })` into `INSERT ... ON CONFLICT (id) DO UPDATE SET id = excluded.id, ...` — every payload column, the PK included, lands in the SET clause. So any table the app upserts on its PK needs `id` in its UPDATE grant list, even though `id` never changes value. `.update()` never names `id` and is unaffected, which is why switching a call from `.update()` to `.upsert()` can break it.
7. **Match the Figma designs.** Do not invent alternative layouts for screens that exist in Figma.
8. **`supabase/schema.sql` says "Safe to re-run", and that claim has to keep being earned.** On 2026-09-23 six places had fallen behind `supabase/migrations/` while the header still promised a no-op, and re-running would have reversed four fixes, worst being both public views losing `closed_at is null` (they are `security_invoker = false` and bypass RLS, so that clause is the ONLY thing hiding a closed account). **Write a migration, change schema.sql in the same pass.** The live database is schema.sql then the migrations in date order; where they disagree the migration wins, and the disagreement is the bug.
9. **Never hand-edit the seven brand PNGs in `assets/`.** `logo.png`, `icon.png`, `favicon.png`, `notification-icon.png` and the three `android-icon-*.png` files are ALL generated by `node scripts/generate-icons.js` from `design-refs/logo-master-transparent.png`. Change the artwork, re-run the script; the fill ratios in it are the specification. `design-refs/` is gitignored, so the master lives on the design machine and the seven outputs are what is committed. **`assets/android-icon-background.png` and `android.adaptiveIcon.backgroundColor` in `app.json` must always state the same colour** — the knockouts in the mark (the ECG line, the gap between heart and V) are transparent holes, so a disagreement shows the wrong colour through them.
   - **THE MARK IS EFFECTIVELY CIRCULAR, and the fill ratios are derived from that, not inherited.** Its ink box is 1203x1122 and the furthest ink pixel is 607px from the centre, so the mark's longest side and the diameter of the circle enclosing it agree to within 1%: a fill of `f` puts the whole mark inside a circle of diameter `1.009 * f`. Every circular-mask question (the adaptive icon's safe zone, the notification shade's disc) is answered by that one number.
   - **The adaptive icon's fill is 0.55, raised from 0.42 on 2026-09-23.** Android guarantees the centre `66/108` (0.611) of an adaptive icon survives every launcher mask, so the largest safe fill is `0.611 / 1.009 = 0.606`. 0.42 was inherited from the previous artwork rather than derived and left the mark floating in a wide empty ring, which is what the owner saw as "the logo is quite small" in the notification shade. `android-icon-monochrome.png` MUST carry the same fill as the foreground, or the themed and normal launcher icons read as two different sizes on one home screen.
   - **`notification-icon.png` is the Android status-bar icon and there had never been one.** `expo-notifications`' `icon` option was unset, so Android silhouetted the launcher icon instead and drew whatever alpha that happened to have. It is a flat WHITE mark on transparency at 96x96, because Android keeps only the alpha and tints the shape with the plugin's `color`. The transparent knockouts are what stop the silhouette reading as a blob, so they matter most here, where the colour is thrown away.
   - **Both of those live in the native manifest and drawable resources, so they need a REAL BUILD.** An OTA update changes neither.


## Conventions

- Data hooks return React Query results; screens never call Supabase directly (only hooks and `lib/`).
- Anything needing a secret or heavy compute goes through `api-client.ts` → serverless API.
- Every feature PR-sized chunk includes tests: Layer 1 scorer and V-Score math must have full unit coverage (Jest).
- Ghanaian context: regions/districts come from `constants/ghana-locations.ts` (16 regions). Phone format is Ghana (+233).
- Error states, loading skeletons, and empty states are required on every data screen (see Figma).
- **The tab bar is a FLOATING PILL and is `position: absolute`.** It therefore reserves no space, so **EVERY SCREEN INSIDE A TAB GROUP** must pad its scroll content with `useTabBarContentPadding()` from `components/ui/tabBarOptions.tsx`, spread LAST so it wins over the stylesheet's own `paddingBottom`. The safe-area inset is a MARGIN under the bar, never padding inside it — a docked bar absorbs the inset by growing; a floating one must leave it empty or the pill overlaps the gesture bar.
  - **"Tab screen" means "screen inside the tab navigator", NOT "screen with a button on the bar".** A screen registered with `href: null` is hidden from the bar and the bar still floats over it. That misreading left 29 of 43 screens unpadded until 2026-09-14, with Sign Out on Settings visible behind the pill and untappable.
  - **A plausible-looking `paddingBottom: spacing.xxl` is ~85px SHORT.** The pill's top edge is at `inset + 76`; the clearance is `inset + 92`. The shortfall exceeds a button's height, so the failure is a completely unreachable control rather than a tight one.
  - **`components/ui/__tests__/tabBarClearance.test.ts` enumerates the three `_layout.tsx` files and fails on any screen that neither clears the bar nor carries a stated exemption.** Add a screen, add the hook — or add it to `EXEMPT` with the reason it has nothing tappable at the bottom. Do not delete the test to make a screen pass.
  - **The bar is inset with `marginHorizontal`, and `left`/`right` DO NOT WORK THERE.** React Navigation pins its bottom bar with `start: 0` / `end: 0`, and in Yoga `start`/`end` outrank `left`/`right` whatever the order of the style array. An inset written as `left`/`right` is therefore parsed and silently discarded, which is why the bar rendered full width through three separate attempts to widen the gap (16, then 28, then 12% of the screen) and why raising the number never changed anything on the device. Fixed 2026-09-18; do not go back to `left`/`right`.
- **Tab icons are Ionicons, in matched outline/filled pairs.** Not MaterialCommunityIcons, which the rest of the app still uses for in-content glyphs. The filled/outline swap is what says "selected"; the coral tint reinforces it.
- **`alignItems: 'center'` is not enough on a row that also sets `flexWrap: 'wrap'`.** `alignItems` centres children within their line; `alignContent` places the line, and defaults to `flex-start` — so a wrapping row pins its single line to the top of the box. Any wrapped row that should look vertically centred needs both.
- **NO RAW ERROR OBJECT EVER REACHES A USER.** Every user-visible error string goes through `humanError()` / `humanErrorOrNull()` in `lib/errorMessage.ts`, never `error.message` directly. supabase-js sets `message` to a stringified copy of the HTTP response when a body is not the JSON it expected, which is how `{"status":500,...}` ended up on the registration screen on 2026-09-12. The function rejects anything that reads as machine output — JSON, a stack, a bare URL, a SQLSTATE, an error code, anything over 300 characters — and maps known failures to sentences. A raw `error.message` is still correct inside a `console.warn`; those are for developers.
- **ONE PASSWORD RULE, in `lib/password.ts`, imported by every screen that sets one.** Enforced: at least 8 characters, at least one letter, at least one number. Nothing else — a rule demanding a symbol reliably produces `Password1!`. `passwordStrength` is a nudge and never a gate. The rule previously lived in `hooks/useAccountSecurity.ts` under a comment claiming registration shared it; registration had its own inline `length < 6`, so the app demanded MORE to change a password than to choose one.
- **Auth screens must apply `insets.bottom` to their scroll content.** There is no tab bar under them to carry it, and 24dp from the bottom of the window is underneath the gesture bar on some handsets and clear of it on others — which is why "Already have an account? Log in" was visible on one phone and not another.
- **NOTHING THAT ANSWERS A BUTTON PRESS MAY SIT AT THE BOTTOM OF THE SCREEN.** Owner's standing rule, given three times and restated emphatically on 2026-09-22 ("never should a notification/btn/alert of anything that shows after something is submitted show at the bottom"). The bottom of a phone is where the thumb is and where the eyes are not, and it is under the floating tab pill; a refusal printed there is indistinguishable from a button that did nothing. Three surfaces, and which one to use is decided by what the message is:
  - **A FAILURE OR A REFUSAL is `ErrorAlert`** (`components/ui/ErrorAlert.tsx`), a centred `AlertDialog` over a dimmed scrim, the same mechanism as the Sign Out confirmation. It has to be read, so it stops the person. Pass the mutation's `error` straight in; dismissal is derived from the error's identity, so a new failure reopens it and the one just acknowledged stays shut. **Never `<Text style={styles.error}>{humanError(x.error)}</Text>` under a submit button again.**
  - **A SUCCESS RECEIPT is `Toast`**, and it is pinned to the TOP under the status bar (moved 2026-09-22; it used to sit above the tab bar). A toast is for something that plainly worked and whose result is already visible.
  - **Inside a bottom sheet it is `SheetError`**, a banner at the TOP of the sheet and OUTSIDE its scroller. A sheet is already a `Modal`, and stacking a second `Modal` on one is the arrangement that misbehaves on Android.
  - **FIELD VALIDATION STAYS INLINE.** "Enter a valid phone number" under the phone box is attached to the control it is about and the person is already looking at it. This rule is about the result of pressing a button, not about a form telling you which box is wrong.
- **EVERY FORM WITH A TEXT FIELD NEEDS A `KeyboardAvoidingView`.** Not just the ones that obviously scroll. The app is edge-to-edge, so the window does not resize when the keyboard opens and a field low on the page is simply covered. The admin review screens (credentials, disputes, organisation detail, sources) and the organisation verification form were all built without one and all hid their reason field behind the keyboard. Use `KEYBOARD_AVOID_BEHAVIOR` from `constants/keyboard.ts`; wrap the SCROLL CONTAINER only, leaving the header, any `DocumentViewer` and the `Toast` outside it, or the toast's safe-area offset is applied twice.
- **`Avatar` carries the verified tick, through one `verified` prop for both roles.** The caller resolves its own truth (`organisation_profiles.verified`, or `volunteer_profiles.verification_status === 'verified'`) and the component only draws it, so the avatar never has to know which role it is rendering. It is deliberately NOT drawn for `documents_pending`: a tick that means "waiting" is a tick somebody will read as "checked".
- **Anything routing INTO a screen inside a tab group must say where it came from.** A tab group keeps no history, so `ScreenHeader` navigates with `replace` to the `from` query param if there is one and to the screen's own `fallback` otherwise. A screen with more than one entry point therefore gets the wrong back destination for every entry point but the default one, and the failure is silent. `notificationDestination()` now attaches `from` to every organisation destination, not just the applicants one, and all seven links into `app/policy.tsx` carry it.
- **NO TYPOGRAPHIC DASHES IN ANYTHING A USER CAN READ.** Owner's standing rule. No em dash and no en dash in screen copy, labels, buttons, toasts, error messages, empty states, the Info Hub, the policy and terms, push text or email bodies. Use a comma, a full stop, a colon, or rewrite the sentence; ranges take a plain hyphen or the word "to". Comments and this file are exempt: the rule is about what reaches a person, not about the source.
  - **`lib/__tests__/userFacingText.test.ts` enforces it and will fail the build.** `node scripts/findUserText.js` prints the same report while you fix them. 63 of them had accumulated across 29 files before the sweep of 2026-09-14.
  - **It parses, it does not grep.** The script walks the TypeScript AST and inspects only string literals, template literals and JSX text, so a dash in a JSDoc block is correctly ignored. A hand-written comment stripper was tried first and produced two false positives and four false negatives, which is how a guard gets switched off.
- **A WORD IS NEVER SPLIT ACROSS LINES.** Owner's standing rule, 2026-09-11. Every screen imports `Text` from `@/components/ui/Text`, never from `react-native` — it sets `textBreakStrategy="simple"` and `android_hyphenationFrequency="none"` so Android's line breaker cannot split a word for a tidier right edge, and caps growth at `MAX_FONT_SCALE`. That is only half the rule: a container narrower than its longest word is still broken by Android as a last resort, so any layout constant that exists *because of the words inside it* (a `minWidth` sized to a label, a `minHeight` sized to two lines) must go through `scaleWithFont()` in `constants/typography.ts`. Where a row cannot be widened, `prefersStackedLayout()` in the same file decides when it becomes a stack instead. **Nothing currently calls it, and that is not an oversight**: `SettingsRow` used to be the worked example and was rewritten on 2026-09-22 to stack its label and value ALWAYS, which removed the competition between two text nodes rather than arbitrating it. `scaleWithFont` and `prefersStackedLayout` are kept because the rule above still stands for the next fixed-width row; they are not evidence that any row needs them today.
- **THE APP MUST WORK AT A LARGE SYSTEM FONT SIZE.** Accessibility settings are the user's choice. `fontSize` scales with them and every other stylesheet number does not, which is the entire class of bug found on 2026-09-11 ("Notificatio / ns", "30% Complet", text escaping its box). `MAX_FONT_SCALE` (1.3) is a ceiling, not a refusal — Android allows 2.0 and stacks a display-size multiplier on top, and no phone layout survives that. Rows that could overflow use `flexWrap: 'wrap'` with a `rowGap`, which changes nothing until they actually overflow.
- **EVERY SCREEN WHOSE CONTENT CAN OUTGROW THE VIEWPORT NEEDS A SCROLL CONTAINER.** A plain flex column fits at the default font size and runs off the bottom of the phone at a large one, with nothing to scroll. It also reads as a *navigation* bug rather than a layout one: a drag that scrolls nothing is still a press to the view under the finger, so trying to reach the bottom activates whatever card is under the thumb. Both Profile tabs had this. `map`, `scan` and `search` are deliberately full-bleed; nothing else may be.
- **`KeyboardAvoidingView` uses `KEYBOARD_AVOID_BEHAVIOR` from `constants/keyboard.ts`, never a `Platform.OS === 'ios' ? 'padding' : undefined` ternary.** That ternary means the component does nothing on Android, which was correct while `adjustResize` shrank the window and stopped being correct when the app went edge-to-edge (Expo SDK 57 / RN 0.86 default, Android 15 enforced): the window no longer resizes, so the keyboard simply covers the field.
- **Give every component real spacing.** When adding a section to a screen, do not insert it flush into the stack — give it proper padding and margins from its neighbours, using the existing `spacing` tokens. This is a standing owner complaint: new boxes kept arriving jammed against each other (Applicant Vetting) or pulled into their neighbour by a negative margin (the Schedule scan button), which makes the app read as unfinished. It applies to **every screen touched**, not just the one being fixed. Cramped layouts are also what cause text truncation on narrow phones.
- Commit style: conventional commits (`feat:`, `fix:`, `chore:`, `test:`).
- **Lint is CLEAN and must stay clean** — both `npx eslint app components hooks lib stores constants types` and `npx eslint api/src` return zero. It was 47 errors / 7 warnings until 2026-09-08, and the cleanup turned up a real hook-ordering bug hiding among the noise, which is the argument for not letting it drift again.
- **`react-hooks/set-state-in-effect` is disabled at TWELVE SITES, each with its own reason, and never in the config.** They are all the same legitimate shape — state seeded or reset from something outside React (a resolved query, a route param, a `visible` prop) where the user's own edits must survive. React's alternative is a real refactor of each, and every one of those effects is already tuned against a specific failure its comment names. **Suppress at the site, never widen it to the config**: a new accidental setState-in-effect anywhere else must still fail.
- **Never write `useRef(new Animated.Value(0)).current`.** It reads a ref during render, which React refuses. Use `useState(() => new Animated.Value(0))` — same single construction, same stable instance, no ref.
- **A hook must never sit below an early return.** `app/(volunteer)/outreach/[id].tsx` had three of them under its loading and error returns, so they were skipped on the first render and called on the next — the "rendered more hooks than during the previous render" crash, which only ever looked fine because the early return unmounted before React compared the two lists.
- **`api/` has no ESLint config of its own** and is linted by the root Expo config, which does not load Next's plugin. A `@next/next/*` disable directive there is reported as an error ("Definition for rule ... was not found"), so do not add one unless Next's own config is added too.
