# Matching engine in full

> Moved verbatim out of CLAUDE.md on 2026-09-24 to keep that file under the size Claude Code loads comfortably. These are still binding project decisions; CLAUDE.md keeps a one-line summary of each and points here.

## Matching Engine (spec is final)

**Score = Skills×35 + Category×20 + Location×20 + Availability×15 + Experience×10** (each component normalised 0–1; total out of 100).

- Skills: matched required skills ÷ **required** skills. **A `support` outreach forces this component to 1.0 for everyone (owner-approved 2026-09-15)**, the same override the category component already carries and for the same reason: a registration desk is not clinical work, and ranking a volunteer on clinical skills for it punished exactly the students and willing helpers the platform exists to include. The wizard now requires skills only when some role is clinical, so the two must stay in step. **The organisation still sees the real skills on the applicant card** - this changes the ranking, not what is shown. NOTE the denominator was never the problem: dividing by the requirement means a thin profile has never been penalised for being thin. The denominator is the requirement, never the larger set — dividing by the larger set penalised breadth (a volunteer holding all 5 required skills plus 15 others scored 5/20 = 0.25). Skills beyond the requirement neither help nor hurt. An outreach with no required skills scores 1.0; a volunteer with no skills against a real requirement scores 0.
- Category: exact = 1.0, related = 0.5, none = 0. Related pairings (symmetric) live in `RELATED_CATEGORIES` in `constants/categories.ts` as the single source of truth, applied by `categoryMatchScore()` there: doctor/nurse/midwife are related to one another; pharmacist↔student; student is additionally related to nurse/doctor/midwife; first_aider and other are related to nothing.
- Location: same district = 1.0, same region = 0.5, different region = 0.
- Availability: **the SHARE of the outreach's days the volunteer is free for**, scaled so that covering `AVAILABILITY_FULL_COVERAGE` (0.5) of them or more scores 1.0. A day counts as covered when `availability_slots` holds a `"{day_weekday}_{slot}"` token whose weekday matches that day and whose slot overlaps **that day's own hours** (morning ≤ 12:00, afternoon 12:00–17:00, evening ≥ 17:00, from the day's `start_time`/`end_time` falling back to the event's). See the continuous-availability section below. **A one-day outreach is unchanged and still scores exactly 1.0 or 0** — one day is covered or it is not, so the scaling leaves both values alone.
- Experience: experienced = 1.0, intermediate = 0.6, beginner = 0.3.

**Reliability multiplier (ordering only).** Candidates are ranked by `matchScore × reliabilityMultiplier`, where the multiplier comes from the volunteer's V-Score band: Elite/Trusted/Active = 1.00, Developing = 0.90, At Risk = 0.70. It is **bounded in (0,1]** — reputation can only ever reduce a ranking, never inflate one, so fit defines the ceiling. New volunteers (70, Active) sit at 1.00: an untested record is not a bad one. Lives in `lib/vscore.ts` (`getReliabilityMultiplier`, `computeRankingScore`) and is applied in `/api/match` mode `score_applicants` only — in `rank_feed` it would be one constant across every row and cannot change the order. The raw match score and the V-Score both stay separately visible to organisations; **the multiplied value is never displayed as a match percentage**, and `applications.match_score` always stores the RAW score.

**Feed pre-filter (scalability).** `rank_feed` fetches candidates before scoring: `status = 'open'`, slots still available, and region ∈ the volunteer's own region + its neighbours (`GHANA_REGION_ADJACENCY` in `constants/ghana-locations.ts`, symmetric, enforced by test). Category, skills and availability are deliberately **not** pre-filtered — a related category still scores 0.5, a partial skill overlap is a real match, and availability edge cases should score 0 rather than vanish. If fewer than `FEED_MIN_CANDIDATES` (5) survive, the search widens to the whole platform (`shouldWidenFeedSearch` in `lib/matching/feedFilter.ts`), so a quiet region never yields an empty feed. The filter changes what is cheap to rank, never what is discoverable.

Layer 1 lives in `lib/matching/layer1.ts` as pure functions (fully unit-testable, no network). Layer 2 lives ONLY in the serverless `/api/match` endpoint: it sends both skill lists to Gemini for semantic equivalence (e.g. "venipuncture" ≡ "blood draw"), replaces only the skills component, caches comparisons in a `skill_match_cache` table, and falls back silently to Layer 1 on any failure.
